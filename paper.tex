\begin{abstract}
Mills' Constant is part of a formula that generates primes and can be used to test the limits and edge cases of computation. In this work, we compute 1,665,460 digits of the Mills' Constant and publicly provide the software to be available for reproduction by assuming the Riemann Hypothesis. The problems arising from computing Mills' Constant include operations with both very large and very small numbers. In the source code, there are methods for numerical computation in Python that build on top of included capabilities. For example, floating point operations in Python have fixed precision by default, and this work achieves arbitrarily large precision limited only by available memory. In addition, this framework consists of optimizations that have produced a 98.41\% reduction in compute time. Further applications can include enhancing the determinism of Large Language Models' temperature parameters through floating-point arithmetic.
\end{abstract}

\section{Introduction}
In 1947, William H. Mills proved a fundamental theorem in number theory showing the existence of a real number $\theta$ such that the floor sequence $\lfloor \theta^{3^n} \rfloor$ yields a prime number for all positive integers $n$ \cite{mills1947}. This expression serves as a popular classic mathematical framework for prime generation pipelines \cite{numberphile}. However, evaluating the precise fractional composition of $\theta$ is computationally difficult. The underlying prime sequences scale at a severe triple-exponential rate where subsequent terms quickly grow to span millions of individual digits \cite{caldwell2005}.

To compute these values, implementations must analyze known prime-gap parameters while assuming the validity of the Riemann Hypothesis to guarantee stable sequence spacing boundaries \cite{caldwell2005}. Historical benchmarks mapped early index subsets, but recent breakthroughs identifying higher sequence offsets ($a(14) = 8436308$) by Propper and Batalov \cite{oeisA108739, batalovRepo} provided the necessary structural criteria to calculate the constant significantly beyond the 555,153-digit boundaries reached in previous open replication experiments \cite{zabeMath}.

This note introduces a Python framework designed to push this computational frontier by resolving exactly 1,665,460 decimal digits of the constant. The open-source replication environment is fully documented and hosted for public distribution \cite{hammadRepo}.

\section{Mathematical Formulation}
Rather than using forward exponentiation, calculating $\theta$ involves determining a sequence of tightening bounds using known Mills primes ($P_n$). The constant can be represented as a limit of these prime configurations:
\begin{equation}
    \theta = \lim_{n \to \infty} P_n^{3^{-n}}
\end{equation}
This allows us to evaluate the value within structured, narrowing intervals defined by:
\begin{equation}
    P_n^{3^{-n}} \le \theta < (P_n + 1)^{3^{-n}}
\end{equation}
The framework programmatically processes these limits by parsing sequence components through targeted database indexes.

\section{Software Architecture and Precision Guarding}
Native programming language architectures evaluate floating-point expressions with fixed binary precision (e.g., standard IEEE 754 64-bit definitions), causing rounding errors when processing deep decimal strings.

\subsection{Arbitrary Precision Scaling}
To bypass these hardware constraints, this software utilizes the multi-precision library \texttt{mpmath} \cite{mpmathIndex}. While standard pure-Python floating-point emulation introduces structural processing loops, this setup integrates \texttt{mpmath} with the compiled C-based \texttt{gmpy2} dependency \cite{mpmathGmpy}. Linking directly with the GNU Multiple Precision Arithmetic Library (GMP) optimizes the mathematical overhead, yielding a 98.41\% reduction in total compute time relative to unoptimized implementations.

\subsection{Catastrophic Cancellation Guard}
An unexpected edge case involving catastrophic cancellation occurs during the execution loop of calculating the $n^{\text{th}}$ root of a targeted prime string \cite{mpmathRoots}. Because \texttt{mpmath} manages internal mathematical states in a binary format, native boundaries experience long strings of consecutive zero bits for floating-point calculations at hyper-extended configurations.

When transforming these raw binary layouts into base-10 (decimal strings), a conversion shift occurs. The mathematical conversion steps can drop the primary ones-place integer by 1 unit, introducing an endless sequence of trailing 9s in subsequent decimal fractions (e.g., yielding $\dots.999999\dots$ instead of the exact rounded representation). During data validation phases, our code includes specific rounding guards to intercept boundary drops and align the base-10 text output with the physical values outlined in \texttt{mpmath} reference specifications.
\section{Computational Verification and Numerical Validation}

To validate the reconstructed decimal representation of Mills' constant, we implemented a numerical verification procedure based on the subsequent terms of the Mills prime sequence. Rather than relying exclusively on comparing the reconstructed constant against an existing decimal representation, this approach evaluates whether the calculated approximation satisfies the expected relationship with the next element in the sequence.

\subsection{Reconstruction of the Known Constant}

Let the Mills prime sequence be defined recursively as:

\begin{equation}
    b_{n+1} = b_n^3 + a_n
\end{equation}

where $b_1 = 2$ and $a_n$ represents the corresponding extension values from OEIS A108739 \cite{oeisA108739}.

Given a known sequence of Mills primes, the constant can be approximated by isolating it from:

\begin{equation}
    b_n = \lfloor A^{3^n} \rfloor
\end{equation}

For the reconstruction, we calculate:

\begin{equation}
    \widehat{A}_n = \sqrt[3^n]{b_n}
\end{equation}

This calculation is performed using the arbitrary-precision \texttt{mpmath.nthroot()} implementation. The internal decimal precision is dynamically configured based on the length of the subsequent Mills prime, with an additional 1,000 guard digits to reduce numerical rounding errors.

\subsection{Subsequent-Term Verification}

The primary verification mechanism evaluates the reconstructed constant against the next known sequence extension.

Given the approximation $\widehat{A}_n$, we calculate:

\begin{equation}
    X = \widehat{A}_n^{3^{n+1}}
\end{equation}

The expected subsequent Mills prime is:

\begin{equation}
    b_{n+1} = b_n^3 + a_n
\end{equation}

Consequently, the verification evaluates:

\begin{equation}
    D = \left\lfloor b_{n+1} - (X + a_n) \right\rfloor
\end{equation}

A successful verification requires:

\begin{equation}
    D = 0
\end{equation}

This condition establishes that the computed subsequent power, after accounting for the known sequence extension, falls within the expected unit interval below the subsequent Mills prime. In particular, it checks that:

\begin{equation}
    b_n^3 - 1 < X \leq b_n^3
\end{equation}

The test therefore provides a numerical consistency check against an additional known sequence term rather than simply reproducing the original input used to calculate the constant.

\subsection{Precision Management and Output Generation}

An important implementation detail concerns the handling of arbitrary-precision numerical representations. The computation retains an additional 1,000 decimal digits internally beyond the precision determined by the subsequent sequence term.

These additional digits serve as guard digits during exponentiation and verification. Following successful verification, the implementation removes the additional precision from the returned decimal representation.

The resulting constants are written to separate output files, \texttt{A\_13.txt} and \texttt{A\_14.txt}, preserving the reconstructed numerical representations for subsequent use.

The verification procedure also addresses an important limitation of arbitrary-precision numerical computation: an internally accurate floating-point result does not necessarily guarantee that its decimal string representation preserves the expected integer boundary. Performing the subsequent-term verification before removing the additional precision helps detect discrepancies introduced by numerical representation and rounding.

\subsection{Scope of Verification}

The experiments demonstrate that the reconstructed approximations satisfy the expected subsequent-term relationships for the supplied Mills prime sequence. They provide computational evidence for the numerical consistency of the resulting representations and demonstrate the practical utility of arbitrary-precision arithmetic for extending the computation.

This verification should be distinguished from an independent primality proof of every sequence element or a formal proof of the Riemann Hypothesis. The procedure validates the numerical reconstruction against the supplied sequence extensions; it does not independently establish the primality of those inputs or the underlying assumptions used to construct the sequence.

\section{Downstream Applications: LLM Determinism}
Beyond standard number theory exploration, the high-precision arithmetic paradigms evaluated by this project provide immediate architectural insights for artificial intelligence optimization. In large language model (LLM) serving frameworks, temperature adjustments scale logit distributions prior to applying a Softmax function:
\begin{equation}
    S_i = \frac{\exp(z_i / T)}{\sum_{j} \exp(z_j / T)}
\end{equation}
When the temperature parameter $T$ approaches near-zero values ($\epsilon \to 0$) to generate deterministic greedy selections, standard fixed-precision hardware frequently triggers underflow errors or catastrophic floating-point cancellations. Applying the arbitrary-precision constraints and radix truncation guards explored in this repository directly allows neural network execution environments to maintain predictable logit selection matrices, ensuring deterministic software output at extreme scaling bounds.

\section{Conclusion}
This framework successfully computes and preserves a 1,665,460-digit representation of Mills' constant. By detailing the interactions between arbitrary-precision scaling environments and internal conversion loops, this research provides an open, optimized testing environment for multi-precision computing and high-performance number theory verification.
